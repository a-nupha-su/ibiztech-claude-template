# โครงเอกสาร Business Requirement (BR) / SRS

เอกสาร BR และ SRS ทุกฉบับใช้องค์ประกอบ หัวข้อ และลำดับตามนี้ โครงถอดมาจากเอกสาร BR จริงฉบับหนึ่งที่ใช้กับลูกค้า
(ราว 100 หน้า · 20+ ตาราง · 70+ รูป) ตัวอย่างประโยคทั้งหมดในไฟล์นี้เป็น **mockup** ของโครงการสมมติ
"ระบบจองคิวร้านตัวอย่าง" ไม่ใช่ข้อความจากเอกสารลูกค้า

- **ตัวสร้าง:** `build_br.py` (รันเปล่า ๆ ได้โครงว่าง `BR-SKELETON.docx`)
- **ตัวอย่าง spec:** `example_spec.py` → `EXAMPLE-BR.docx`

## บทที่ 4 — เข้าใจลักษณะระบบ (เรียง H2 ตาม journey ที่ผู้ใช้เดินจริง)

1. `1. ภาพรวมสำหรับ<ระบบ> (Overview)` — ย่อหน้าสรุปความต้องการที่รวบรวมจากทีมลูกค้า → **รูปภาพรวมระบบ** (caption "รูปที่ 1 แสดงภาพรวม…")
   → ประโยค "จากรูปที่ 1 แสดงให้เห็น… ประกอบด้วย" → **ตาราง `องค์ประกอบ · รายละเอียด`**
2. `2. โมดูล (Modules)` — ประโยคนำ → **ตาราง `ชื่อโมดูล · รายละเอียด`** (ระบบภายนอก/บริการที่ต้องเชื่อม เช่น CMS, OTP, Payment, ระบบส่งข้อความ)
3. `3. … ` ถึง `N. …` — ขั้นตอนหลักของ journey ตามลำดับ (ตัวอย่าง mockup: แสดงบริการ → เลือกสาขา/วันเวลา → ยืนยันตัวตนด้วย OTP →
   กรอกข้อมูลผู้จอง → Consent → สรุปก่อนยืนยัน → ชำระมัดจำ → ฟังก์ชันหลังจอง (เลื่อนนัด · ยกเลิก · ประวัติการจอง))
   - แตก H3 เป็น `3.1)` `3.2)` และ H4 เป็น `3.4.1)` — **เลขพิมพ์ไว้ในข้อความหัวข้อเอง** ไม่ใช้ auto-numbering
   - แยกกรณีตามกลุ่มบริการ/ผู้ใช้เป็นหัวข้อย่อย (`4.2.1) กรณีบริการรายครั้ง` · `4.4.1) สำหรับลูกค้า` / `4.4.2) สำหรับเจ้าหน้าที่`)
   - ทุกขั้นมีรูปหน้าจอหรือ flow + caption "รูปที่ N …" และมักตามด้วย **ตารางเงื่อนไข**:
     `No. · บริการ · Input Condition · เงื่อนไขการแสดง · หมายเหตุ` หรือ `บริการ · <ข้อมูลที่ต้องกรอก> · … · หมายเหตุ`

## บทที่ 5 — requirement แต่ละข้อ (H2 `N. <ชื่อความต้องการ>`) โครงตายตัว 6 ส่วน

| H3 (ลงท้ายด้วย `:`) | เนื้อหา |
|---|---|
| `วัตถุประสงค์:` | ประโยคเดียว ว่าทำเพื่อให้ใครทำอะไรได้ |
| `สิทธิผู้ใช้งาน:` | role ที่ใช้ (ลูกค้า / เจ้าหน้าที่ / ผู้ดูแล) |
| `หน้าจอ:` | ชื่อหน้าจอ + รูป + caption |
| `ฟังก์ชันการทำงาน:` | H4 `1)` `2)` … = ขั้นตอนการทำงานทีละขั้น · H5 `1.1)` `1.2)` = รายละเอียด/กรณีย่อย (พบ / ไม่พบ / Pop-up / อีเมล) · ยกตารางจากบทที่ 4 มาอ้างได้ ("ยกตารางมาจากหัวข้อ 3.4.1") |
| `เงื่อนไขการทำงานของระบบ:` | H4 เป็นข้อ ๆ = business rule และ validation (เช่น เบอร์โทร 10 หลัก ขึ้นต้น 0) และสิ่งที่ต้องเก็บลง DB |
| `การจัดการข้อมูล Setup ที่เกี่ยวข้อง:` | H4 เป็นข้อ ๆ = ของที่หลังบ้านต้องตั้งค่าได้ (โครงสร้างเลขที่เอกสาร · ผู้รับผิดชอบ · บริการ/แพ็กเกจ · Promotion · Banner · วันหมดอายุ · เทมเพลตอีเมล) |

## บทที่ 6 — Functional Design ต่อฟังก์ชัน (H2 `N. ฟังก์ชันจัดการ <X>`)

`วัตถุประสงค์:` · `สิทธิผู้ใช้งาน:` · **รายละเอียดของข้อมูล** = ตาราง `No. · Field Name · Description · M/O · Condition/Comment`

## แนวการเขียนและภาษา

**น้ำเสียง** ภาษาไทยทางการแบบเอกสารงานระบบ บรรยายเป็นบุคคลที่สาม ไม่ใช้ "เรา/คุณ" · เรียกลูกค้าของโครงการว่า
**"ทางทีมงาน<ชื่อบริษัทลูกค้า>"** และเรียกผู้ใช้ปลายทางว่า **"ลูกค้า"** · ผู้ปฏิบัติงานหลังบ้านคือ **"เจ้าหน้าที่ (หลังบ้าน)"**
· ประโยคสั้น-กลาง ต่อกันด้วย `ซึ่ง` `โดย` `เพื่อ` แทนการขึ้นย่อหน้าใหม่

**ผสมไทย-อังกฤษ** คำเทคนิคและชื่อหน้าจอ/ฟีเจอร์เขียนอังกฤษตรง ๆ ไม่แปล: `Set / Setup` · `Default` · `Submit` · `Pop-up` ·
`Drop Down List` · `Landing` · `Package` · `Promotion` · `Log` · `Journey`
· ครั้งแรกที่พูดถึงให้วงเล็บอีกภาษากำกับ: `การยืนยันตัวตน (OTP)` · `ภาพรวมระบบจองคิว (Booking overview)`

**การเขียนในตาราง**
- ช่อง "รายละเอียด" ของตารางองค์ประกอบขึ้นต้นด้วย `คือส่วนของ…` · ตารางโมดูลขึ้นต้นด้วย `เป็นระบบ…` และบอกว่า **อยู่ภายใต้การดูแลของใคร**
  ("…อยู่ภายใต้การดูแลของทีมงาน<ลูกค้า>") — แยกความรับผิดชอบให้ชัดตั้งแต่ตาราง
- ช่องเงื่อนไขเขียนเป็นรายการ `- …` หรือ `1. …` ในเซลล์เดียว · ค่าเริ่มต้นเขียนแบบ `ระบบ Default = 1 ครั้ง`
- สถานะเขียนเป็นรหัส + คำอธิบาย: `สถานะ 0 – ไม่สามารถจองได้ …` · `สถานะ 1 – …` · `สถานะ 2 – …`

**การอ้างถึงของบนหน้าจอ**
- ข้อความ/ปุ่ม/คำที่ผู้ใช้เห็น ใส่อัญประกาศคู่ `“…”`: `“ยืนยันการจอง”`
- ปุ่มเขียน `กดปุ่ม <ชื่อปุ่ม>` · ชื่อหน้าจอเขียนอังกฤษตาม UI (`หน้า Service Detail`, `หน้า My Booking`)
- ของที่ไม่บังคับต่อท้าย `(ถ้ามี)` · อ้างข้ามหัวข้อด้วยเลข: `(ยกตารางมาจากหัวข้อ 3.4.1)` · อ้างรูปด้วย `จากรูปที่ N แสดงให้เห็น…`
